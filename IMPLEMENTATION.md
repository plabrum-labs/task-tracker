# tt — implementation

Companion to `DESIGN.md`, which owns the data model and the product decisions. This
file owns the stack, the package layout, and the CLI/TUI surface.

Module: `github.com/Plabrum/tt`. Binary: `tt` (verified free on `PATH`).

## Stack

| Concern | Choice | Why |
|---|---|---|
| Language | Go 1.26 | |
| Schema | Ent | Declarative in Go — `Fields()` / `Edges()`, typed traversals |
| Migrations | Atlas CLI, versioned, diffed from the Ent schema | Expresses backfills and renames, which auto-migrate cannot at any flag setting |
| Driver | `modernc.org/sqlite` | Pure Go, `CGO_ENABLED=0`, trivial cross-compile |
| CLI | stdlib `flag` + subcommand dispatch | Twelve verbs doesn't justify `cobra`; teaches how dispatch works |
| Table output | `text/tabwriter` (stdlib) | |
| TUI | `bubbletea`, `bubbles`, `lipgloss` | In v0 — bare `tt` opens it |
| Tests | stdlib `testing`, table-driven, against in-memory SQLite | |

Dependencies: Ent, the SQLite driver, the bubbletea trio, and their transitive deps. No CLI
framework, no color library, no ORM beyond Ent.

### Connecting

Ent doesn't know `modernc.org/sqlite`, so open the `*sql.DB` yourself and hand it over:

```go
db, err := sql.Open("sqlite", dsn)
drv := entsql.OpenDB(dialect.SQLite, db)
client := ent.NewClient(ent.Driver(drv))
```

The DSN carries the pragmas, because they are **per-connection** and `database/sql`
pools connections — setting them once after `Open` protects only the first one:

```
file:$DB?_pragma=foreign_keys(1)&_pragma=journal_mode(WAL)&_pragma=busy_timeout(5000)
```

- `foreign_keys(1)` — off by default in SQLite for backward compatibility with
  pre-3.6.19 databases. We want the cascades in `DESIGN.md` to actually fire.
- `journal_mode(WAL)` — persistent once set, but harmless to repeat.
- `busy_timeout(5000)` — a concurrent writer gets a retry window instead of an
  immediate `SQLITE_BUSY`. Relevant because an agent loop and your terminal may write
  at the same moment.

`db.SetMaxOpenConns(1)` is set. SQLite allows one writer, and serialising in Go produces
clearer behaviour than surfacing `SQLITE_BUSY`. Two things downstream rest on it: reads
skip the transaction (see below), and `WithTx` must roll back on a panic, since an
abandoned transaction holds the only connection there is.

The path is percent-escaped into the URI rather than concatenated. The default store sits
under `$HOME`, so a `?` or `#` in a directory name is not ours to rule out, and an
unescaped one truncates the path and drops the pragmas that follow it.

### Migrations

Generated by the Atlas CLI, which is what both Ent and Atlas document:

```
just db-migrate <name>      # atlas migrate diff --env local <name>
```

`atlas.hcl` holds the wiring — `src = "ent://ent/schema"`, a throwaway in-memory dev
database, `dir = "file://migrations"` — so the recipe stays a one-liner. Atlas replays
`migrations/` onto the dev database to compute current state, diffs the Ent schema
against it, and writes the next versioned file plus `atlas.sum`.

The dev URL uses `_fk=1`. That is the Atlas CLI's own SQLite driver; the
`_pragma=foreign_keys(1)` form is modernc's, and applies to `DSN` in `internal/db`
rather than to anything here.

`migrate diff` exits 0 whether or not it found a difference — a difference *is* the file
it writes. `just db-check` is built on that: it diffs under a fixed name, fails if a file
appeared, and removes it (plus re-hashes `atlas.sum`) on the way out. Tests build their
schema with `Schema.Create` rather than by replaying `migrations/`, so a forgotten
`db-migrate` breaks no test — `db-check` is what catches it. It is deliberately not part
of `verify`, which must stay runnable without the Atlas binary.

**Applying is a separate step**, `just db-upgrade`, run by the Atlas CLI. `internal/db`
does not migrate: `Open` sets the pragmas, pings, and hands back a client. A database
that has never been migrated opens fine and fails on the first query.

This reverses an earlier decision to apply on startup. That was meant to spare a personal
CLI the "run migrations first" failure — but buying it cost a hand-written
`migrate.RevisionReadWriter` over an `atlas_schema_revisions` table, because Atlas OSS
publishes only a no-op one and keeps the real implementation in an unimportable
`cmd/atlas/internal/` package. Roughly 430 lines of machinery, pinned to an Atlas
pseudo-version, on a path neither Ent nor Atlas documents.

The consequence is real and belongs to Phase 2: a fresh database now gives
`no such table: projects`, so the CLI needs an explicit first-run and upgrade story
rather than inheriting one from `Open`.

## Package layout

Feature-based, with `internal/` for application-private code.

```
main.go                  config, wiring, frontend selection. No verb parsing.

ent/
  schema/                hand-written Ent schemas
  …                      generated, committed

internal/
  db/
    open.go              DSN + pragmas + connect. Does not migrate.
    tx.go                WithTx helper
  errs/
    errs.go              the four sentinels every layer returns
  app/
    api.go               the API struct and its constructor
    capture.go           Add
    read.go              Show, List
    lifecycle.go         Start, Done, Drop, Note
    refs.go              Dep, Undep
    taxonomy.go          Label, Milestone
    edit.go              Edit, Rm
  issue/
    model.go             domain types + Ent-free views (Issue, Detail, AddParams)
    enum.go              the checked ent↔domain enum conversions
    repository.go        persistence, backed by Ent
    service.go           issue rules, as package-level funcs taking *ent.Client
  ref/
    model.go
    repository.go
    service.go           link/unlink, cycle checks, closable guard
  comment/               starts as one file; splits when it earns it
  project/               includes cwd → slug scope inference
  milestone/
  label/
  query/                 cross-feature reads: List, Eligible, Next, progress, counts
  frontmatter/           $EDITOR form parse/render — shared by cli and ui
  dbtest/                throwaway client for tests; schema via Schema.Create

cli/
  add.go  ls.go  show.go  …    one file per verb
ui/                      bubbletea

migrations/              committed .sql + atlas.sum, read by the Atlas CLI
atlas.hcl                the `local` env: ent:// source, dev database, dir
```

Dependency flow: **`cli`/`ui` → `internal/app` → feature package → Ent → SQLite.**

One file per verb group in `app/`, because four Phase 2 lanes adding methods to one file
is a worse conflict than the wiring struct it replaced ever was.

**The rule the compiler enforces: `cli` and `ui` never import `ent`.** Ent entities and
query builders stop at the repository layer; frontends see only feature view types. Beyond
keeping the frontends honest, this keeps ent's lazily-loaded edges out of render code —
`issue.Edges.Labels == nil` means either "not loaded" or "has no labels", and a `View`
function has no way to tell which.

### Feature packages are leaves; `app` composes

Per-feature packages hit real import cycles here, so the direction is fixed by ownership
rather than left to whoever writes the call.

**Services never call services.** A feature package exports package-level funcs taking an
`*ent.Client`; it does not reach into another feature. That is what makes the first two
rules below facts rather than rules — with composition in `app`, `issue` has no reason to
import `project` and does not.

A rule that must not be skippable lives wherever its data lives. One feature's data means
inside the feature — `AddParams.validate` is called by `issue.Create`, not by `app.Add`.
Two features' data means the API method calls it. The TUI still cannot route around either,
because the API is all a frontend can see.

1. **Taxonomy never depends on work.** `project`, `milestone`, and `label` must not import
   `issue`. Their aggregate reads — milestone progress, label open-counts — live in
   `query/`, not in their own packages.
2. **Cross-feature reads of substance live in `query/`.** A feature may read tables it does
   not own, because every one of them imports `ent` and `ent` knows every entity — but only
   for narrow existence and status checks. Anything larger is two features writing
   overlapping queries against one table.
3. **`issue` may depend on `ref`; `ref` must not depend on `issue`.** The `done` guard is an
   issue rule that needs ref data, so it's `ref.AssertClosable(ctx, cl, issueID)` called from
   `app.Done`. Cycle detection is a pure walk over ref rows and needs nothing from `issue`.
   The subtask rollup, which does need issue status, is a `query/` read.

### One API method, one transaction

`tt add "x" -l backend -M v1 --sub-of 12` upserts a project, upserts a milestone, resolves
or creates labels, inserts an issue, and inserts a ref — one atomic unit that no single
feature owns.

**An API method that writes opens exactly one `db.WithTx`. An API method that only reads
passes the client straight through.** Reads skip the transaction because
`SetMaxOpenConns(1)` means a `BEGIN` serialises the whole process behind itself and buys
nothing in-process; the only exposure is a cross-process writer leaving a derived flag one
refresh stale, which is not worth a BEGIN/COMMIT on the hottest path. Read-then-write
(`Start`, `Done`) is a write and gets a transaction — its safety comes from the
compare-and-swap predicate either way.

Feature funcs take the client they are handed and never begin a transaction of their own,
so a composed call and a standalone call run the same code. Ent in an *internal* signature
is fine; ent in `cli`/`ui` is not. `internal/issue/enum.go` is the deliberate exception:
its conversions take and return ent enum types, which a frontend still cannot name without
importing ent.

### Absence

**A zero value means "absent" only when the zero value is not itself meaningful; otherwise
use a pointer.** No magic sentinels — no `0`, no `-1`, no `"none"`. Outputs encode absence
as `null` via a pointer and never use `omitempty`: the `--json` keys are the agent
contract, and a key that vanishes when its value is empty forces every consumer to
distinguish "absent" from "empty" by hand.

So `AddParams.SubOf` is `*int` and `Issue.ClosedAt` is `*time.Time`, while strings and
slices keep `""`/`nil` — empty is not a legal `Title`, `Milestone` or label.

### Errors

`internal/errs` holds the vocabulary. Every failure below the frontends wraps one sentinel,
and each frontend owns its own mapping — the CLI to an exit code, the TUI to a message — so
neither ever matches on message text.

| Sentinel | Meaning | Exit code |
|---|---|---|
| `errs.ErrInvalid` | bad user input | 2 |
| `errs.ErrNotFound` | id or name doesn't exist | 3 |
| `errs.ErrConflict` | a rule refused | 1 |
| `errs.ErrEmpty` | nothing eligible | 4 |

`Invalidf`/`NotFoundf`/`Conflictf`/`Emptyf` wrap with `%w`, so a call site stays one line.
The sentinel → exit-code mapping lives in `cli/exit.go`.

### Interfaces

None to start. Tests run against real in-memory SQLite with migrations applied, so mock
seams buy nothing here. Add an interface when a second implementation or a real boundary
shows up, not in anticipation of one.

### Consequences of `Ref` being an edge schema

`Blocks`/`BlockedBy` goes through `Ref` (see `DESIGN.md`), which buys `kind` but costs
three things worth writing down before they surprise us:

1. **No composite primary key, so duplicates are possible.** A plain Ent M2M generates a
   join table with `PRIMARY KEY (blocked_id, blocker_id)`; an edge schema is an entity with
   its own int `id`, so nothing stops two identical `(blocked, blocker)` rows.
   `ref.Link` must upsert — look for an existing `Ref` and update its `kind` rather than insert a
   second edge. Add a unique index on the pair in the Ent schema so the database enforces
   it too.
2. **Linking is explicit.** `AddBlockedByIDs()` isn't available through an edge schema;
   you create a `Ref` row. Slightly more code in exactly one place, which is fine.
3. **Eligibility is unaffected.** `HasBlockedByWith(...)` still traverses, and it
   deliberately ignores `kind` — every ref blocks, which is the whole point of subtask
   being a subset rather than a parallel relation. Only kind-*filtered* reads go through
   `Ref`, and those are display concerns: the subtask list in `show` and the rollup below.

**Settled in Phase 0 — the generated spelling.** `Through` on a self-reference does work,
so `DESIGN.md`'s predicate is the real one: `issue.HasBlockedByWith(...)` and
`issue.HasBlocksWith(...)`, traversing `refs` directly. No `ref.HasBlockerWith(...)`
indirection is needed for eligibility. For kind-filtered reads there are also
`issue.HasBlockerRefsWith(ref.KindEQ(...))` and `issue.HasBlockedRefsWith(...)`, which
reach the `Ref` rows themselves — `blocker_refs` are the refs where the issue is the
blocker, `blocked_refs` the ones where it is blocked.

Two things in `ent/schema/issue.go` are load-bearing and shouldn't be "tidied":

- The edge carries an explicit `StorageKey(edge.Columns("blocker_id", "blocked_id"))`.
  For a self-reference both of `Ref`'s edges point at `Issue`, so ent cannot infer which
  backs which side and matches the relation columns against `Ref`'s edge-field names
  instead. Without the storage key, codegen fails with `missing edge-field`.
- The two directions are declared as separate edges rather than chained through `From()`.
  Ent's loader copies an assoc's storage key onto a chained inverse and then rejects the
  pair as having two storage keys.

### Subtask semantics

Two behaviours the design's `kind` field implies but doesn't yet specify:

- **`done` on a parent with open subtasks warns and refuses, `--force` overrides.** A dep
  gates *starting*; a subtask gates *finishing*. Without this check `kind` is decorative —
  the edge already blocks pick, so `subtask` would change nothing but a heading in `show`.
  The refusal message lists the open children. Implemented as `ref.AssertClosable`, called
  from `app.Done`.
- **Progress rollup.** An issue with subtask refs renders a `3/5` badge in `ls`, the TUI
  list, and `show`. One grouped count over `Ref` where `kind = subtask`; computed at read
  time, never stored. It joins refs to issue status, so it lives in `query/`.

Both sit below the frontends, so the CLI and TUI get them identically — the TUI physically
cannot skip the guard.

### Creating subtasks

`dep <parent> on <child> --subtask` links two issues that already exist. That's the wrong
shape for the common case, which is decomposing something you're looking at right now, so
there's also:

- `add "title" --sub-of <id>` — create and link in one step, inheriting the parent's
  project and milestone.
- `S` in the TUI — same thing, inline title prompt against the selected issue.

Decomposition is a capture-time action. Making it a two-step link is the kind of friction
that ends with people writing subtasks into the body as a markdown checklist.

## Entry point: the lazygit model

**Bare `tt` opens the TUI. `tt <verb> …` is the CLI.** Same split as `lazygit` and
`zellij action`. The interactive surface gets the shortest invocation because browsing
is the most common human action; the verbs stay available for scripting and agents.

This is safe only because `ls` remains an explicit verb — `tt ls | grep`,
`tt ls --json | jq` are unaffected, since nobody pipes the bare command.

Two conditions:

1. **No TTY and no args ⇒ run `ls`, don't launch the TUI.** `tt | cat`, `tt > out.txt`,
   or `tt` inside a CI step must produce a plain list rather than terminal escape codes
   or a hang. Check `os.Stdout` before deciding what bare `tt` means.
2. **Until the TUI exists, bare `tt` aliases `ls`.** The alias is one line and gets
   replaced when the TUI lands mid-v0 — no throwaway work.

### Dispatch

`main.go` switches on `os.Args[1]`: a known verb dispatches to `cli`, nothing dispatches to
`ui`, an unknown verb is a usage error (exit 2). Each verb owns a `flag.FlagSet`.

Global flags (`-A`, `--project`, `--json`) are registered per-verb via a shared helper
rather than parsed before the subcommand — stdlib `flag` stops at the first non-flag
argument, so `tt -A ls` wouldn't work without hand-rolling a pre-parser, and it isn't
worth it.

### Output rules

- **TTY detection** drives styling. Piped or redirected output is plain: no color, no
  box drawing, no truncation-with-ellipsis. `tt ls | grep`, `tt ls | wc -l` must behave.
- Honor `NO_COLOR`.
- `--json` implies plain, emits one object or an array, and is a stable contract —
  changing a key is a breaking change to the agent interface.
- Tables via `tabwriter`: `id`, flags (`!`, `⊘` blocked), title, labels, milestone.
- Long titles truncate only when attached to a TTY, and only to terminal width.

### Exit codes

Codes are part of the agent contract, so they're specified rather than incidental:

| Code | Sentinel | Meaning |
|---|---|---|
| 0 | — | Success |
| 1 | `errs.ErrConflict` | Error |
| 2 | `errs.ErrInvalid` | Usage error |
| 3 | `errs.ErrNotFound` | Not found |
| 4 | `errs.ErrEmpty` | Nothing eligible (`tt start` on an empty or fully-blocked backlog) |

4 is the one that earns its keep: it lets an agent loop distinguish "no work left, exit
cleanly" from "something broke" without parsing stderr.

`cli/exit.go` owns the mapping. An error matching no sentinel is a 1.

### Input conventions

- `-e` opens `$EDITOR` on a temp markdown file. For `add` it's the body; for `edit` it's
  a small document with the metadata as frontmatter and the body below, parsed on save:

  ```markdown
  ---
  title: fix the thing
  labels: [backend, bug]
  milestone: v1
  priority: hi
  ---
  Body markdown here.
  ```

  Frontmatter round-trips, so editing is declarative in the same spirit as the schema.
- `-` as an argument reads from stdin: `git log -1 | tt note 12 -`.
- `rm` prompts to confirm on a TTY; requires `-f` when not attached to one, so a script
  can't silently delete.
- IDs are bare ints; accept `#12` as well, since you'll paste it out of a comment.

## TUI

The primary human surface, reached by bare `tt`. In v0, not a later phase — it owns the
default invocation.

**Scope: one screen, several arrangements of it.** Not multi-pane, not a Linear clone.

### Three layouts, `tab` cycles

| Layout | Shape | Min width |
|---|---|---|
| `list` | Flat list, detail below the selection | — |
| `split` | Flat list left, detail pane right | 100 |
| `board` | Three columns by status, no detail pane | 90 |

`tab` cycles through the layouts **that fit the current viewport**; ones that don't are
skipped rather than offered and then broken. `list` has no minimum — it's the always-works
fallback, and under ~20 rows its detail becomes a full-screen swap on `enter` instead of a
pane.

One axis, one key, three values. An earlier draft had this as two orthogonal axes
(arrangement × detail placement) plus a derived column flow, which produced twelve states
and grouping modes nobody asked for. Grouping by milestone or label is a **filter**, not a
layout — `M` and `L` — which is what you'd reach for anyway.

If the terminal is resized so the current layout no longer fits, drop to the widest one
that does and show a quiet marker in the status bar (`split→list`) so it reads as
deliberate. **The stored preference is not overwritten**, so widening restores it.

Minimum usable viewport is ~40×12. Below that, print a message and exit rather than
rendering something unusable.

### Internal model

The generality lives in the code, not in the user-facing choice. All three layouts render
from the same structure:

```go
type Column struct {
    Title  string
    Issues []query.Row
}
// list, split → one column;  board → three
func columns(rows []query.Row, by GroupBy) []Column
```

So navigation is **one** implementation over `[][]Issue` — `j`/`k` within a column, `h`/`l`
between them, and a one-column layout is just the case where `h`/`l` are no-ops. Adding a
fourth layout later is a renderer plus a `GroupBy`, not a new navigation path.

### Invariants

1. **Selection is an issue ID, never a cursor index.** Filtering, refreshing, switching
   layout, and closing an issue all reshuffle the rows. Cursor position is derived from the
   ID each render, degrading to the nearest surviving row when the selected issue
   disappears. Needed regardless of layout count — layout switching just makes it obvious.
2. **`columns()` is pure** — no I/O, no Model access. Table-driven testable, and it also
   backs `ls --group`.
3. **`fits(layout, w, h) bool` is pure**, which keeps the whole responsive story to one
   small tested function instead of size checks sprinkled through `View`.
4. **Layout state persists** in `$XDG_STATE_HOME/tt/ui.json` — layout, show-done,
   all-projects. Reopening `tt` should look like you left it. This is state, not config, so
   it doesn't belong in a config file.
5. **Column drop order** when width is tight, after `id` and `title` are satisfied: drop
   `milestone`, then `labels`, then flags. `id` and `title` never drop; `title` truncates
   last. The `3/5` subtask badge sits with the flags.
6. **The list stays flat — subtasks are not indented under parents.** Nesting reopens tree
   rendering, sibling ordering, collapse state, and the question of where a
   multi-parent subtask appears. A parent shows `3/5`; `enter` on it lists the children in
   the detail pane. If flat browsing turns out to be genuinely worse, indentation is a
   renderer change, not a model change.

Recompute on every `tea.WindowSizeMsg`.

### Keymap

| Key | Action |
|---|---|
| `j`/`k`, arrows | Move within column |
| `h`/`l` | Move between columns (`board` only; no-op elsewhere) |
| `tab` | Cycle layout: list → split → board, skipping any that don't fit |
| `enter` | Focus the detail pane for scrolling; `esc` returns |
| `s` | Start selected |
| `d` | Done selected |
| `x` | Drop selected (`doing` → `todo`) |
| `n` | New issue — inline title prompt, `ctrl-e` to open `$EDITOR` instead |
| `S` | New subtask of the selected issue — same prompt, links on create |
| `e` | Edit selected in `$EDITOR` (frontmatter form, via `tea.ExecProcess`) |
| `c` | Add a comment |
| `D` | Link a dependency — prompt for the blocker id |
| `/` | Filter, substring, live |
| `L` | Filter by label |
| `M` | Filter by milestone |
| `a` | Toggle showing done |
| `A` | Toggle all projects |
| `?` | Cheatsheet overlay for the current context |
| `q` | Quit |

`l` is column-right rather than label-filter, so label filtering takes `L` — vim movement
wins the lowercase key.

### Capture

`n` opens a one-line prompt at the bottom; `enter` creates the issue with a title only
and returns to the list with the new row selected. Body, labels, and milestone come later
via `e`. This is the fastest path from thought to stored, which is the whole reason the
tracker survives contact with real use.

`ctrl-e` from that prompt escalates to the full `$EDITOR` frontmatter form for when you
already know it's a big one.

### Architecture

The part of bubbletea people get wrong:

- `Model` holds `query.Row` / `issue.Detail` values, the selected issue **ID**, filter
  string, layout, and mode (`normal` | `prompt` | `filter` | `detail`). Never an ent client.
- `Update` never blocks. Every DB call is a `tea.Cmd` calling a service and returning a
  message — `issuesLoadedMsg`, `startedMsg`, `errMsg`. This is why the ent boundary matters.
- `View` is pure formatting over `Model`. No I/O, no queries.
- `$EDITOR` hand-off uses `tea.ExecProcess`, which suspends and restores the terminal
  correctly. Don't shell out directly.
- `lipgloss` styles are package-level vars, defined once.
- Mode determines which keys are live, and the `?` overlay reads from the same table that
  dispatches them — one source of truth, so the cheatsheet can't drift.

### On lazygit as a reference

Worth being precise, because it will bite when you go read the source: **lazygit uses
`jesseduffield/gocui`, not bubbletea.** It's a Go TUI, but not an example of the
framework we're using — gocui is imperative view-and-keybinding registration, bubbletea
is Elm-architecture message passing. Its code won't transfer line for line.

What does transfer, and is worth stealing:

- **The entry-point split** above.
- **A `?` cheatsheet overlay** listing every binding in the current context. Lazygit's
  discoverability comes almost entirely from this, and it costs one view function.
- **Single static binary**, which our `modernc.org/sqlite` choice already gives us.
- **Every action reachable from the list** — you never leave the main view to do the
  common thing.

What not to copy: lazygit's config surface is enormous (custom commands, full keybinding
remapping, theming). That's earned by a large user base, not by a personal tool.

### Not building

Mouse support, drag-to-reorder (there's no rank column to reorder — see
`DESIGN.md` on pick order), more than two panes, a config file for keybindings, custom
commands, theming.

## Testing

- **The layer worth testing is the one that owns a rule**, against a real in-memory SQLite
  with migrations applied — no mocks, no interfaces invented for test seams. That splits in
  two: feature-package tests call the package-level funcs with `dbtest.Client` and no
  transaction, covering mapping, predicates, ordering, validation and slugification;
  `internal/app` tests use `dbtest.API` and cover what only composition can break —
  atomicity, and one rule reaching another feature's data.
- Table-driven tests per invariant, one helper that returns a fresh migrated client.
- The ent boundary is tested by reflection over `app.API`'s method set: no parameter or
  return type, walked recursively, may be declared under `github.com/Plabrum/tt/ent`.
- The enum conversions are tested against `ent/migrate/schema.go`'s generated column
  descriptors, so the value set under test is the one the database accepts. A hand-written
  list cannot do that — whoever forgets the constant forgets the list entry too.
- The cases that matter: cycle rejection, eligibility with a chain of blockers,
  compare-and-swap under two concurrent `Start` calls, project auto-create, label
  auto-create, cascade delete.
- Ref-specific cases: linking the same pair twice updates one row instead of creating two,
  `subtask` and `dep` block eligibility identically, `done` refuses on a parent with an open
  subtask and succeeds with `--force`, rollup counts only `kind = subtask`, and a subtask
  under two parents counts toward both.
- CLI tests are golden-file comparisons on stdout with `--json`, which is exactly the
  contract an agent depends on.
- TUI tests cover the three pure functions and nothing else:
  - `columns()` for each `GroupBy`, including empty input and a status with zero issues.
  - Selection resolution — the selected ID survives a layout switch, and degrades to the
    nearest surviving row when the issue is filtered out, closed, or deleted.
  - `fits()` at 40×12, 80×24, 90×24, 100×30, 200×60 — the boundary cases where `tab` should
    start and stop offering `split` and `board`.

## Build order

1. `go.mod`, Ent schema for the five entities, first Atlas migration.
2. `internal/db` open, `internal/errs`, `internal/app`, then `project`, `issue`,
   and `query` far enough for `Add`, `Show`, `List`.
3. `add`, `ls`, `show` end to end — the point where it's usable for capture.
4. `start`, `done`, `drop`, `note` — the lifecycle, plus `--json` and exit code 4.
5. `columns()`, selection resolution, and `fits()` as pure functions, with tests. No
   bubbletea yet.
6. TUI: `list` layout only, `j/k`, `s`, `d`, `n`, `/`. Flip bare `tt` to it.
7. `split` and `board`, `tab` cycling, resize handling, persisted `ui.json`.
8. `edit` with `$EDITOR` frontmatter (CLI and `e` in the TUI), `rm`, bulk ids.
9. `dep` with cycle detection and `--subtask`, `add --sub-of`, the rollup badge, the `done`
   guard, `label`, `milestone`, and the TUI bindings for them.

Steps 1–3 are the milestone that decides whether this tool survives: if capture isn't
frictionless, nothing after it matters.

The TUI lands at 6, after the lifecycle verbs exist for it to call and after the pure
functions it depends on are tested — but before the long tail of organize verbs, so it
gets used early enough to find out what's actually wrong with it. Step 5 existing on its
own is deliberate: the parts most likely to have bugs are testable without a terminal.
